# Daily Cyber Patch - 2026-07-20

Mode: Public defensive guidance. No private environment data included.

## Executive Summary

- CISA's live Known Exploited Vulnerabilities catalog has not advanced since July 16. The July 19 deadlines for FortiSandbox CVE-2026-39808 and CVE-2026-25089 and on-premises SharePoint Server CVE-2026-58644 are now overdue; applicable owners should patch or isolate and complete compromise assessment rather than treating a version update as historical clearance.
- GitHub's public advisory API returned 362 malware records published after the previous completed patch cutoff through 2026-07-20T18:22:35Z: 99 npm and 263 NuGet records, with no PyPI match in the same query. This is a publication count, not a count of distinct campaigns; the batch includes large related namespaces and test-data-like names. Search exact package identities without installing, importing, restoring, or executing them.
- Today is the revised backport date for safer `actions/checkout` behavior in supported versions and a configuration-plus-runtime brownout date for outdated self-hosted runners in GitHub Enterprise Cloud with Data Residency. SHA-, minor-, and patch-pinned checkout users must update deliberately, and the backport does not make every privileged workflow safe.
- Package controls must cover configuration processing, restore/install behavior, import or runtime activation, editor and agent startup, and later conditional execution. Script suppression helps, but it does not prevent registry-configuration leaks or malicious code that activates after installation.

## Copy/Paste Assessment

Run only checks that match systems you own or administer. These commands enumerate package names and configuration locations; they do not print credential values.

Assessment notes:

- A manifest or lockfile match establishes possible exposure, not execution. Correlate it with install, restore, import, build, test, editor, endpoint, runner, and CI history.
- No lockfile match does not clear globally installed, dynamically fetched, cached, vendored, previously removed, or editor-managed packages.
- The advisory count includes a large bulk publication and related namespaces. Do not infer one campaign, one actor, or equivalent risk from the count alone.
- Do not investigate suspected malware by importing, installing, restoring, or executing it on a normal workstation. Use the organization's isolated analysis and incident-response process.
- A lifecycle-script block does not stop package-manager configuration processing, package imports, CLIs, tests, build plugins, editor activation, or later execution.
- Verify appliances and SharePoint versions through vendor-supported inventory. Do not probe systems you do not own or administer.

## Copy/Paste Remediation

For a Node project with a reviewed lockfile and no evidence of compromise:

```bash
# Rebuild from the reviewed lockfile while suppressing lifecycle scripts during initial inspection.
npm ci --ignore-scripts
npm audit --audit-level=high
npm test
```

Package and registry controls:

- Prefer npm v12's default-deny install controls. Review and approve only required lifecycle scripts, Git dependencies, and remote dependencies; commit the reviewed allowlist.
- Keep a release cooldown for routine version updates. Do not delay security updates merely to match the routine cooldown.
- Upgrade affected pnpm 10 deployments to 10.34.2 or later and affected pnpm 11 deployments to 11.5.3 or later; prefer a current supported release after reviewing its changelog.
- Bind each registry credential to its exact intended host and scope. Remove deprecated unscoped authentication and do not let repository-controlled configuration select the destination for a credential defined elsewhere.
- Treat lockfile integrity drift, unexpected registry hosts, publisher changes, and newly requested install or runtime permissions as security-review events.

If a malicious package was installed, restored, imported, or executed, or if package-manager configuration could reach credentials:

1. Stop using the affected environment for credentialed development, builds, releases, and deployments.
2. Preserve relevant endpoint, process, package-manager, CI, source-control, registry, identity, and signing logs under the incident-response policy.
3. Rebuild the workstation or runner from a known-good image rather than trusting package removal alone.
4. Restore a reviewed lockfile and use maintainer-confirmed packages and releases.
5. Rotate credentials reachable from the affected process through the relevant account, cloud, registry, signing, or secret-manager interface. Revoke active sessions and review audit logs.
6. Rebuild and compare artifacts from reviewed source before restoring publication or deployment access.

For GitHub Actions, OIDC, caches, and runners:

```yaml
# Start every workflow with no token permissions; grant only what each job requires.
permissions: {}
```

- Never check out or execute untrusted pull-request code in a privileged `pull_request_target`, `workflow_run`, or comment-triggered job.
- Upgrade supported `actions/checkout` versions through a reviewed commit SHA. Version 1 does not receive today's backport, and SHA-, minor-, or patch-pinned workflows do not receive floating-tag updates automatically.
- Treat `allow-unsafe-pr-checkout` as a high-risk exception requiring documented review and isolation.
- Do not assume read-only cache-token changes cover artifacts, non-default scopes, custom caches, or every trigger. Verify provenance before a privileged job restores untrusted state.
- Protect every branch and tag that can trigger a release. Require reviewed changes and environment approval for publication.
- Pin third-party actions to reviewed commit SHAs and use dependency tooling to keep pins current.
- Separate `id-token: write`, repository writes, cache writes, artifact promotion, and package publication into minimal jobs.
- Use ephemeral isolated runners for untrusted code. Update runner binaries, images, bootstrap automation, and cached templates together.
- Validate immutable OIDC owner and repository IDs, audience, branch, reusable workflow, and environment conditions in non-production.

For MCP, agents, package selection, and editor extensions:

- Deny new packages, servers, tools, extensions, endpoints, and permissions by default; approve the exact publisher, repository, version, endpoint, and capability.
- Treat tool descriptions, package documentation, retrieved documents, issue text, web pages, and persistent memory as untrusted data, never as authorization.
- Authenticate local control planes, validate origins, bind network services to the narrowest interface, and isolate browsing from privileged tool execution.
- Require human approval for credential use, external writes, publication, deployment, destructive actions, and scope expansion.
- Bind each agent or MCP server to a dedicated least-privilege identity and narrow network destinations.
- Revoke approval when metadata, ownership, binary, endpoint, dependencies, or requested permissions change.
- Disable workspace extension recommendations and automatic task execution for untrusted repositories until reviewed.

For exploited products:

- Follow CISA-required actions and current vendor advisories. Patch supported systems, isolate unsupported systems, and discontinue products that cannot be mitigated.
- Treat FortiSandbox CVE-2026-39808 and CVE-2026-25089 and SharePoint CVE-2026-58644 as overdue.
- Investigate relevant authentication, administrative, application, and network activity. Patching closes the vulnerability but does not erase prior exploitation.

Verify operationally:

- A clean ephemeral CI run succeeds from the reviewed commit using updated lockfiles, pinned actions, and a current runner image.
- A staged release requires the intended protected branch, workflow, identity, and approval; an unauthorized non-production source cannot publish.
- Cloud federation succeeds only for the intended immutable GitHub subject and audience; a deliberately unauthorized request is denied.
- Package-registry, GitHub, cloud, identity, and signing logs show no unexplained actions after containment and credential rotation.
- MCP and agent tests demonstrate that untrusted content cannot grant permissions, add tools, change durable memory without review, reach privileged local control planes, or trigger external writes without approval.
- Editor inventory matches the organization allowlist and endpoint tooling reports no blocked or quarantined extension.
- Product owners record remediated version, deployment date, exposure review, and incident-triage result for every applicable KEV item.
