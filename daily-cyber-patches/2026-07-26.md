# Daily Cyber Patch - 2026-07-26

Mode: Public defensive guidance. No private environment data included.

## Executive Summary

- Treat today’s bulk npm malware-advisory publication as an inventory and incident-response trigger. The GitHub Advisory Database API returned its 500-record cap for malware records published after the prior patch cutoff; all 500 returned records were for unique npm package names, while a parallel pip/PyPI query returned zero. This is not evidence of 500 distinct campaigns or 500 newly compromised projects.
- Prioritize environments that installed affected Mini Shai-Hulud package versions. Public advisories describe install-time credential theft, CI workflow injection, agent-hook persistence, and a background service. Package removal alone is not sufficient after execution.
- Close known credential paths before dependency execution: upgrade affected pnpm versions, review repository-controlled package-manager configuration before running installs, adopt npm v12’s default-deny install behavior, and isolate untrusted CI jobs from OIDC, caches, artifacts, secrets, and persistent runners.
- CISA KEV remains at catalog version `2026.07.24`. Check Point SmartConsole CVE-2026-16232 and Microsoft SharePoint CVE-2026-50522 are overdue; WordPress CVE-2026-60137 is due August 4 and KNX CVE-2023-4346 is due July 29.

## Copy/Paste Assessment

Run only the checks that match your environment. These commands should not print secret values.

```bash
# Set this to your local workspace before running checks.
export WORKSPACE_ROOT="<WORKSPACE_ROOT>"
cd "$WORKSPACE_ROOT"
```

```bash
# Find package manifests, lockfiles, and repository-controlled package-manager configuration.
find "$WORKSPACE_ROOT" -type f \( \
  -name package.json -o -name package-lock.json -o \
  -name pnpm-lock.yaml -o -name pnpm-workspace.yaml -o \
  -name yarn.lock -o -name requirements.txt -o \
  -name pyproject.toml -o -name .npmrc \
\) -not -path '*/node_modules/*' -not -path '*/.venv/*' -print
```

```bash
# Review package lifecycle hooks and non-registry dependency sources without running them.
rg -n '"(preinstall|install|postinstall|prepare)"[[:space:]]*:' \
  -g 'package.json' -g '!**/node_modules/**' "$WORKSPACE_ROOT" || true

rg -n '"[^"]+"[[:space:]]*:[[:space:]]*"(git\\+|github:|gitlab:|https?://|file:)' \
  -g 'package.json' -g '!**/node_modules/**' "$WORKSPACE_ROOT" || true
```


Assessment cautions:

- Do not infer one actor, one campaign, current installation, execution, or equal severity from advisory counts, similar names, or a concentrated publication timestamp.
- Do not investigate suspected malware by installing, importing, restoring, or executing it on a normal workstation.
- An install-script block does not stop registry configuration processing, package imports, CLIs, tests, plugins, editor activation, MCP startup, agent tools, native executables, or later execution.

## Copy/Paste Remediation

For a Node project with a reviewed lockfile and no evidence of compromise:

```bash
# Rebuild from the reviewed lockfile while suppressing lifecycle scripts during initial inspection.
npm ci --ignore-scripts
npm audit --audit-level=high
npm test
```

Package and registry controls:

- Upgrade pnpm to a fixed release before running it in untrusted or newly obtained repositories. Treat project `.npmrc`, workspace registry declarations, proxy settings, and package-manager plugins as executable trust decisions.
- Prefer npm v12’s default-deny behavior for dependency scripts, native builds, Git dependencies, and remote dependencies. Approve only the exact packages and sources required by the build.
- Use a routine release cooldown so brand-new package versions do not enter production immediately. Keep urgent security updates on a separately reviewed path.
- Pin direct and transitive dependencies with reviewed lockfiles and hashes where supported. Re-review changes in publisher, ownership, registry host, resolved file set, permissions, dependencies, lifecycle hooks, and runtime behavior.
- Prefer short-lived trusted publishing over long-lived registry tokens. Protect the workflow, environment, branch, repository identity, and human approval that can invoke the publisher.
- Use staged publishing or an equivalent reviewed promotion gate for high-impact packages and release jobs.

If a malicious package or extension was installed, imported, restored, or executed:

1. Stop using the affected environment for credentialed development, builds, releases, and deployments.
2. Isolate the environment and preserve relevant endpoint, process, editor, package-manager, CI, source-control, registry, identity, agent, and signing logs under the incident-response policy.
3. Rebuild the workstation or runner from a known-good image rather than trusting package or extension removal alone.
4. Restore reviewed lockfiles, extensions, MCP servers, agent tools, workflow files, caches, artifacts, and startup configuration from known-good sources.
5. Rotate credentials reachable from the affected process through the relevant account, cloud, registry, signing, or secret-manager interface. Revoke active sessions and review audit logs.
6. Rebuild and compare release artifacts from reviewed source before restoring publication or deployment access.

For GitHub Actions, OIDC, caches, and runners:

```yaml
# Start every workflow with no token permissions; grant only what each job requires.
permissions: {}
```

- Never execute untrusted pull-request code in a privileged `pull_request_target`, `workflow_run`, comment-triggered, release, or publication job.
- Separate repository writes, `id-token: write`, cache writes, artifact promotion, signing, and publication into minimal reviewed jobs.
- Pin third-party actions to reviewed full commit SHAs and use dependency tooling to keep those pins current.
- Protect every branch, tag, environment, and reusable workflow that can publish or deploy. Require review for production environments.
- Validate immutable owner and repository IDs, audience, branch, environment, and reusable-workflow conditions in cloud trust policies. Remove obsolete name-only subjects after a verified migration.
- Use ephemeral isolated runners for untrusted code. Update runner binaries, base images, bootstrap automation, and cached templates together. GitHub Enterprise Cloud with Data Residency reaches full runner-version enforcement on July 31.
- Treat caches and artifacts crossing trust levels as untrusted inputs. Verify their origin and content before privileged consumption.

For MCP, agents, and editor extensions:

- Deny new packages, servers, tools, extensions, endpoints, and permissions by default. Approve the exact publisher, repository, version, endpoint, tool metadata, and capability.
- Treat tool descriptions, parameter schemas, returned content, package documentation, retrieved files, issue text, web pages, code comments, workspace rules, and durable memory as untrusted data, never authorization.
- Open unfamiliar workspaces in Restricted Mode. Review tasks, settings, extension recommendations, MCP configuration, hooks, and executable paths before granting trust.
- Revoke approval whenever ownership, binary, dependencies, endpoint, tool description, schema, or requested permissions change.
- Bind each agent or MCP server to a dedicated least-privilege identity and narrow network destinations. Prefer sandboxed standard-input/output transport for local servers.
- Require human approval for credential use, external writes, publication, deployment, destructive actions, and scope expansion.
- Validate OAuth token issuer, audience, resource, scope, expiry, and client consent. Do not pass tokens through to downstream services.
- Authenticate local control planes, validate browser origins, bind network services to the narrowest interface, and isolate browsing or untrusted content from privileged tool execution.

For exploited products:

- Follow CISA-required actions and current vendor advisories. Patch supported systems, isolate unsupported or unmitigated systems, and discontinue products that cannot be secured.
- Treat Check Point SmartConsole CVE-2026-16232 and Microsoft SharePoint CVE-2026-50522 as overdue since July 25. WordPress CVE-2026-63030, Langflow CVE-2026-0770, and DD-WRT CVE-2021-27137 are overdue since July 24.
- Prioritize KNX CVE-2023-4346 before July 29 and WordPress CVE-2026-60137 before August 4 where applicable.
- Investigate relevant authentication, administrative, application, endpoint, and network activity where exposure existed. Patching closes the vulnerability but does not erase prior exploitation.

```bash
git diff --check
```


Verify operationally:

- A clean ephemeral CI run succeeds from the reviewed commit using reviewed lockfiles, pinned actions, and a current runner image.
- A staged release requires the intended protected branch, workflow, immutable identity, and approval; an unauthorized source cannot publish.
- Cloud federation succeeds only for the intended immutable GitHub subject and audience; a deliberately unauthorized request is denied.
- Package-registry, GitHub, cloud, identity, endpoint, and signing logs show no unexplained actions after containment and credential rotation.
- MCP and agent tests demonstrate that untrusted content cannot add tools, change permissions, alter durable memory without review, reach privileged control planes, or trigger external writes without approval.
- Editor inventory matches the approved publisher and version list, and unfamiliar repositories remain restricted until configuration review is complete.
- Product owners record remediated version, deployment date, exposure review, and incident-triage result for every applicable KEV item.

## Not Applicable / Not Tested

- This is passive, public defensive guidance, not a scan of any private repository, workstation, runner, cloud account, registry, editor, MCP server, agent, Check Point deployment, SharePoint farm, WordPress site, KNX environment, or production system.
- No private dependency graph, installed package set, endpoint telemetry, workflow history, cloud trust policy, secret store, registry account, or vulnerability-scanner result was inspected.
- The GitHub Advisory Database query reached its 500-record response cap. The 500 returned entries were unique npm package names, with 480 sharing the same publication minute; the result is therefore reported as “at least 500 returned records,” not a complete count.
- The parallel filtered pip/PyPI query returned zero records from the prior cutoff through research time. This does not prove absence from PyPI or complete ecosystem coverage.
- Several Mini Shai-Hulud advisories published today describe compromise activity from May 2026. Advisory publication time is not the same as package compromise, upload, installation, or execution time.
- Representative package identities are examples for safe manifest matching, not a complete denylist. Use the live advisory feed and approved dependency tooling for current matching.
- PyPI says consumers should not yet rely on the new 14-day upload restriction as a verifiable release-closure property; Upload 2.0 and staged-preview semantics remain future work.
- CISA KEV deadlines apply directly to US federal civilian agencies. Other organizations should use KEV inclusion as a strong prioritization signal and follow their own obligations.
- Vendor affected-version matrices, product-specific indicators, and exploit details were not reproduced. Consult current vendor advisories for exact applicability.
- The July 31 self-hosted-runner enforcement date cited here applies to GitHub Enterprise Cloud with Data Residency. Other GitHub offerings have different dates.
- AI-assisted intrusion claims rely partly on vendor observations and evolving attribution. The recommendations do not depend on claims of fully autonomous attacks.
- MCP and tool-poisoning studies are research evidence, not proof that every client or deployment is vulnerable in the same way.
