# Daily Cyber Patch - 2026-08-11

Mode: Public defensive guidance. No private environment data included.

## Executive Summary

- CISA KEV catalog version `2026.08.10` is current. Progress LoadMaster CVE-2026-8037 and Fortinet FortiOS CVE-2025-68686 passed their August 10 deadlines; TeamCity CVE-2026-63077, Langflow CVE-2026-9198, Tomcat CVE-2026-34486, and both current N-central issues also remain overdue.
- A GitHub Advisory Database snapshot on August 11 returned 72 malware records published after the previous scheduler cutoff: 61 npm and 11 PyPI records covering 70 unique package names. This is catalog activity, not a count of campaigns, installations, executions, or compromises.
- New records include developer-, runtime-, editor-, crypto-, and established-library-themed names. Match exact package identity, registry, scope, publisher, version, and resolved artifact; do not infer trust from a familiar-looking name.
- Install hooks are only one execution surface. Imports, CLIs, tests, editor activation, MCP startup, agent hooks, Python startup files, native modules, scheduled execution, and later runtime retrieval require separate containment and verification.
- AI-assisted attacks are increasing attacker speed and iteration, while public evidence still supports human-directed operations more strongly than universal autonomous intrusion. Defenders should shorten patch and identity-response cycles without weakening review or authorization gates.

## Copy/Paste Assessment

Run only checks that match your environment. These commands report filenames, package identities, configuration lines, or workflow metadata; they are not intended to print secret values.

```bash
# Set this to the repository or workspace you are authorized to review.
export WORKSPACE_ROOT="<WORKSPACE_ROOT>"
cd "$WORKSPACE_ROOT"
```

```bash
# Find package manifests, lockfiles, and repository-controlled package-manager configuration.
find "$WORKSPACE_ROOT" -type f \( \
  -name package.json -o -name package-lock.json -o \
  -name npm-shrinkwrap.json -o -name pnpm-lock.yaml -o \
  -name pnpm-workspace.yaml -o -name yarn.lock -o \
  -name requirements.txt -o -name pyproject.toml -o \
  -name poetry.lock -o -name uv.lock -o -name .npmrc \
\) -not -path '*/node_modules/*' -not -path '*/.venv/*' -print
```

```bash
# Review lifecycle hooks and non-registry dependency sources without running them.
rg -n '"(preinstall|install|postinstall|prepare)"[[:space:]]*:' \
  -g 'package.json' -g '!**/node_modules/**' "$WORKSPACE_ROOT" || true

rg -n '"[^"]+"[[:space:]]*:[[:space:]]*"(git\\+|github:|gitlab:|https?://|file:)' \
  -g 'package.json' -g '!**/node_modules/**' "$WORKSPACE_ROOT" || true
```


Assessment cautions:

- Do not infer one actor, one campaign, current installation, execution, or equal severity from advisory counts, similar names, or concentrated publication timestamps.
- Advisory publication time is not package upload, installation, execution, or compromise time.
- Do not investigate suspected malware by installing, importing, restoring, or executing it on a normal workstation.
- Install-script blocking does not stop imports, CLIs, tests, plugins, editor activation, MCP startup, startup-file processing, native modules, hooks, scheduled tasks, or later execution.
- Registry scanning, marketplace badges, provenance, signatures, and OIDC attest selected trust properties; none proves that source, workflows, dependencies, artifacts, or runtime behavior are benign.
- Verify affected product versions through vendor-supported inventory. Do not probe systems you do not own or administer.

## Copy/Paste Remediation

For a Node project with a reviewed lockfile and no evidence of compromise:

```bash
# Rebuild from the reviewed lockfile while suppressing lifecycle scripts during initial inspection.
npm ci --ignore-scripts
npm audit --audit-level=high
npm test
```

For a Python project with a reviewed lockfile and no evidence of compromise:

```bash
# Create a clean environment, then use the project's approved lockfile workflow.
python -m venv .venv-review
. .venv-review/bin/activate
python -m pip install --upgrade pip
python -m pip check
python -m pip list
```

Do not reinstall or import a suspected package merely to inspect it. Use the package index, advisory record, retained artifact, or an isolated malware-analysis process approved by your incident-response team.

Package and registry controls:

- Enable package-malware matching across supported ecosystems. Deduplicate advisory bursts without losing package name, ecosystem, version, source, and publication time.
- Use a release cooldown so brand-new versions do not enter production immediately. Keep urgent security updates on a separately reviewed path.
- Prefer npm v12's default-deny behavior for dependency scripts, native builds, Git dependencies, and remote dependencies. Approve only exact required packages and sources.
- Upgrade pnpm to a fixed release for CVE-2026-55180 and scope registry credentials to an explicit host. Treat checksum refresh as a reviewed exception.
- Pin dependencies with reviewed lockfiles and hashes where supported. Re-review publisher, ownership, registry host, resolved files, permissions, dependencies, lifecycle hooks, native modules, and runtime behavior.
- Prefer short-lived trusted publishing over long-lived registry tokens. Protect the workflow, environment, branch, repository identity, and human approval that can publish.

If a malicious package, extension, MCP server, or agent tool was installed, imported, restored, or executed:

1. Stop using the affected environment for credentialed development, builds, releases, and deployments.
2. Isolate it and preserve relevant endpoint, process, editor, package-manager, CI, source-control, registry, identity, agent, and signing logs under the incident-response policy.
3. Rebuild the workstation or runner from a known-good image rather than trusting component removal alone.
4. Restore reviewed lockfiles, environments, extensions, MCP servers, tools, workflows, caches, artifacts, startup files, scheduled tasks, and hooks from known-good sources.
5. Rotate credentials reachable from the affected process through the relevant account, cloud, registry, signing, or secret-manager interface. Revoke active sessions and review audit logs.
6. Rebuild and compare release artifacts from reviewed source before restoring publication or deployment access.

For GitHub Actions, OIDC, caches, and runners:

```yaml
# Start every workflow with no token permissions; grant only what each job requires.
permissions: {}
```

- Treat a held run as a security review queue, not a routine confirmation prompt.
- Never execute untrusted pull-request code in a privileged `pull_request_target`, `workflow_run`, comment-triggered, release, or publication job.
- Separate repository writes, `id-token: write`, cache writes, artifact promotion, signing, and publication into minimal reviewed jobs.
- Pin third-party actions to reviewed full commit SHAs and keep pins current.
- Protect every branch, tag, environment, and reusable workflow that can publish or deploy. Require review for production environments.
- Validate immutable owner and repository IDs, issuer, audience, branch, environment, and reusable-workflow conditions in cloud trust policies.
- Use ephemeral isolated runners for untrusted code. Update runner binaries, base images, bootstrap automation, and cached templates together.
- Treat caches and artifacts crossing trust levels as untrusted inputs. Verify origin and content before privileged consumption.
- Enable secret scanning and push protection where available. Detection requires provider-side revocation or rotation and activity review; deleting the latest copy is not sufficient.

For MCP, agents, and editor extensions:

- Deny new packages, servers, tools, extensions, endpoints, and permissions by default. Approve exact publisher, repository, version, endpoint, metadata, and capability.
- Treat tool descriptions, schemas, returned content, package documentation, retrieved files, issue text, web pages, code comments, workspace rules, and durable memory as untrusted data, never authorization.
- Review the complete local MCP startup command before execution. Sandbox the server, restrict filesystem and network access, and do not expose unauthenticated local services to browser-reachable origins.
- Require HTTPS for production authorization endpoints, exact redirect-URI matching, per-client consent, short-lived state, token audience validation, and protected-resource binding. Do not pass upstream tokens through to downstream services.
- Restrict OAuth metadata discovery and redirect destinations with validated egress policy so they cannot reach private, loopback, link-local, or cloud-metadata addresses unless explicitly required and isolated.
- Open unfamiliar workspaces in Restricted Mode. Enable agent and local-MCP sandboxing where supported; restrict file and network access.
- Keep auto-approval scoped to the session. Require manual approval for terminal execution, network fetches, credential use, external writes, publication, deployment, destructive actions, and scope expansion.
- Revoke approval whenever ownership, binary, dependencies, endpoint, tool description, schema, permissions, hooks, or durable-memory behavior changes.

For exploited products:

- Follow CISA-required actions and current vendor advisories. Patch supported systems, isolate unsupported or unmitigated systems, and discontinue products that cannot be secured.
- Apply vendor-fixed releases for LoadMaster CVE-2026-8037 and FortiOS CVE-2025-68686. Restrict administrative reachability and complete exposure and forensics review.
- Update TeamCity On-Premises to `2025.11.7` or `2026.1.3`, or apply JetBrains' supported security patch plugin where an immediate update is impossible.
- Upgrade Langflow OSS `1.0.0` through `1.10.0` to `1.10.1` or later.
- Apply N-central 2026.3 HF1 build `2026.3.1.7` where applicable and complete N-able's exposure and incident-triage steps.
- Upgrade affected Tomcat point releases according to the supported branch advisory; `9.0.116` and `10.1.53` are specifically affected, with fixes in `9.0.117` and `10.1.54`.
- Investigate relevant authentication, administrative, application, build, endpoint, artifact, signing, and network activity where exposure existed. Patching does not erase prior exploitation.

## Verification

```bash
# Confirm the intended repository-only change set.
git status --short
git diff --check
```

```bash
# Confirm representative package identities are absent after remediation.
rg -n -i '(^|["/ ])(newtun|safe-local-env-loader|kit-vim-map|@openzeppelin-4/contracts|@openzeppelin-5/contracts|euler-sdk|morpho-sdk|joule-btp-extension|dlmm)(["/@ <]|$)' \
  -g 'package.json' -g 'package-lock.json' -g 'npm-shrinkwrap.json' \
  -g 'pnpm-lock.yaml' -g 'yarn.lock' -g 'requirements*.txt' \
  -g 'pyproject.toml' -g 'poetry.lock' -g 'uv.lock' \
  . || true
```

Verify operationally:

- Dependency tooling matches reviewed lockfiles against the current malware-advisory feed, and advisory bursts are deduplicated without losing package/version matches.
- A clean ephemeral CI run succeeds from the reviewed commit using reviewed lockfiles, pinned actions, and a current runner image.
- A deliberately untrusted workflow remains held or denied and cannot reach secrets, OIDC, write tokens, privileged caches, protected artifacts, or persistent runners.
- A staged release requires the intended protected branch, workflow, immutable identity, and approval; an unauthorized source cannot publish.
- Cloud federation succeeds only for the intended issuer, immutable GitHub subject, and audience; a deliberately unauthorized request is denied.
- Package-registry, GitHub, cloud, identity, endpoint, and signing logs show no unexplained actions after containment and credential rotation.
- MCP authorization tests reject wrong audiences, mismatched redirect URIs, cross-user state handles, private-network metadata targets, and unapproved local startup commands.
- MCP and agent tests show that untrusted content cannot add tools, change permissions, alter durable memory without review, or trigger external writes without approval.
- Editor inventory matches the approved publisher and version list, and unfamiliar repositories remain restricted until configuration review is complete.
- Product owners record remediated version, deployment date, exposure review, and incident-triage result for every applicable KEV item.

## Not Applicable / Not Tested

- This is passive, public defensive guidance, not a scan of any private repository, workstation, runner, cloud account, registry, editor, MCP server, agent, or production system.
- No private dependency graph, installed package set, endpoint telemetry, workflow history, cloud trust policy, secret store, registry account, or vulnerability-scanner result was inspected.
- The advisory snapshot returned 72 malware records covering 70 unique package names after the previous scheduler cutoff: 61 npm and 11 PyPI records. Concentrated publication timestamps and duplicate identities may reflect catalog processing. These are not counts of distinct campaigns, new compromises, installations, or executions.
- Representative package identities are examples for safe manifest matching, not a complete denylist. Use the live advisory feed and approved dependency tooling for current matching.
- The selected package advisories establish the listed identities and versions; they do not prove that every similarly named package, MCP server, agent, or editor tool is malicious.
- GitHub's held-workflow protection applies to selected potentially malicious runs in public repositories on GitHub.com. It does not cover every run or GitHub Enterprise Server.
- CISA KEV deadlines apply directly to US federal civilian agencies. Other organizations should use KEV inclusion as a strong prioritization signal and follow their own obligations.
- Vendor affected-version matrices, product-specific indicators, and exploit details were not reproduced. Consult current vendor advisories for exact applicability.
- AI-assisted intrusion claims rely partly on vendor observations and evolving attribution. The recommendations do not depend on claims of fully autonomous attacks.
- MCP and tool-poisoning studies are research evidence, not proof that every client or deployment is vulnerable in the same way.
- Source quality: KEV, vendor advisories, GitHub records, specifications, and product documentation are primary sources for listed facts. Threat-intelligence vendors have first-party visibility but selective telemetry; academic MCP studies establish tested risk classes, not universal deployment impact.
